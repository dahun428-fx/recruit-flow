# Feedback Rules (개인 선호 규칙 대장)

소유자가 이력서·경력기술서·자기소개서·커버레터 작업 중 준 피드백을 일반화해
축적하는 **개인 선호층** 대장이다. `writing-guidelines.md`가 보편 원칙층이라면,
이 파일은 소유자 한 사람의 검증된 취향이다.

## 운영 규칙

- **우선순위**: 이 대장의 active 규칙이 `writing-guidelines.md`와 충돌하면
  **이 대장이 이긴다.** (no-fabrication 원칙만은 예외 없이 상위.)
- **범위**: 산출물(글)의 품질 선호만 담는다 — 어투·문장·내용·구조.
  시각/레이아웃 취향은 `DESIGN.md`에 직접 반영하고 여기에는 포인터 한 줄만.
  트러블슈팅은 `docs/troubleshooting/`, 회사별 타게팅 판단은
  `target-companies.md`가 정본이다. 회사별 규칙은 이 대장에 넣지 않는다.
- **일반화 우선**: 지엽적 피드백이 오면 새 규칙 추가보다 기존 규칙을
  일반화해 갱신하는 것이 기본 동작이다. 카테고리 신설은 소유자 승인 필수.
- **수집**: 세션 중 일반화 가능한 피드백이 나오면 즉시 규칙 후보를 한 줄로
  제안하고, 소유자가 승인한 것만 기록한다. 무단 기록 금지.
- **기록 주체**: 이 파일은 소유자 승인 후 최상위 에이전트만 수정한다.
  서브에이전트(writer/tailor 등)는 이 파일을 편집하지 않는다.
- **상태 모델**: 강도 `MUST`(반드시) / `NEVER`(절대 금지) / `PREFER`(기본값,
  어길 땐 이유 명시). 상태 `active` / `retired`. **삭제는 없다** — 해제할 땐
  retired로 바꾸고 날짜와 이유를 남긴다. 재활성화는 상태만 되돌린다.
- **적용 범위**: 기본은 모든 문서 전역. 문서 종류 한정이 필요할 때만
  `범위:` 필드를 붙인다 — 이력서/경력기술서/자기소개서/커버레터 중
  하나 이상(가운뎃점 구분). 조건부 적용은 `조건:` 필드에 한 줄로.
- **소프트 캡**: active 규칙 총량 ~30개. 초과하면 새 규칙 추가 시점에
  통합 후보를 함께 제안한다. 새 규칙 추가 시 기존 규칙과의 모순을 검사하고,
  충돌하면 어느 쪽이 최신 취향인지 물어 한쪽을 retire한다.
- **강제 지점**: `writer`/`tailor`는 드래프트 전에 active 규칙을 읽고 따른다.
  `reviewer`는 active `MUST`/`NEVER`를 규칙 ID로 대조해 위반을 blocking으로
  보고하고, `PREFER` 위반은 의도적인지 확인만 한다.

## 규칙 형식

```markdown
### T-01 · 어투 · PREFER · active
규칙 문장 한 줄 (일반화된 형태).
- 예: "나쁜 예" → "좋은 예"          (선택, 권장)
- 출처: YYYY-MM-DD 어떤 작업에서     (선택)
- 범위: 자기소개서                   (선택, 없으면 전역)
```

ID 접두: `T`=어투, `S`=문장, `C`=내용, `F`=구조. retired 규칙은 제자리에
두고 상태만 바꾼 뒤 `- 해제: YYYY-MM-DD 이유` 한 줄을 추가한다.

### T-01 · 어투 · MUST · active

표현과 어색한 번역투를 피한다.
- 출처: 2026-07-07 두산로보틱스 이력서 수정 세션 ("AI가 쓴 것처럼 보이는
  문장… 실제 개발자가 직접 쓴 것처럼 자연스럽게 다듬어줘")

### T-02 · 어투 · PREFER · active
소극적·방어적 서술보다 직무 요건에 맞춘 적극적(어필형) 어조를 쓴다 —
단 검증된 사실 범위 안에서만.
- 출처: 2026-07-06 ("좀더 공격적으로 써줄 수 있어 직무에 맞게?")

### T-03 · 어투 · MUST · active
근사치는 한정어로 정확히 표기하고("약", "~대", "여 건", "수준"), 잠재
성과는 "…이 가능한" 어형으로 실현 성과와 구분해 서술한다.
- 예: "600여 건", "신규 화면 개발 10주 → 2주 단축이 가능한 템플릿 정비"
- 출처: 2026-06~07 전 초안 공통 어형 (예시는 S-01 금지어 반영해 갱신)

### T-04 · 어투 · PREFER · active
담당 단계의 앞뒤(API·오류·배포·운영)로 확장한 오너십을 명시적으로
프레이밍하고, 수치가 없는 성과는 "책임 범위 확장"으로 서술한다.
- 예: "화면 구현을 넘어 API 응답 구조·배포 전후 검증까지 함께 설계"
- 출처: CJ ENM·NHN·밀리 요약부 공통 패턴

### T-05 · 어투 · MUST · active

하다체("~했다/~단축했다")는 반말로 읽히므로 쓰지 않는다. 실행·성과
bullet의 명사형 종결(S-04)은 그대로 유지한다.
- 출처: 2026-07-24 GS리테일 AX 이력서 수정 ("어미가 다 반말체야")

## 문장 (S)

### S-01 · 문장 · NEVER · active
AI 상투구를 쓰지 않는다: "데이터 흐름", "품질 흐름", "자동화 파이프라인",
"기반 구조 구축", "공통 구조 확보", "하나의 품질 흐름으로 연결",
"기여하고자 합니다", "클린 아키텍처 지향" 및 이에 준하는 추상 상투구.
- 판정 기준: 행위 주체·구체 대상·근거 없이 관념어만 조합된 구절은
  상투구로 간주한다.
- 출처: 2026-07-06~07 사용자가 금지 목록 직접 제시

### S-02 · 문장 · PREFER · active
본문에 보충 설명용 괄호를 넣지 않는다. 필요한 내용은 문장에 녹이거나
삭제한다. 단, 다른 규칙이 요구하는 괄호는 예외다: 단축률 보조 표기(S-03),
JD 키워드 태그(S-06), SI 소속 병기(C-07).
- 예: "(주요 프로젝트: 삼성물산…, 상세는 경력기술서)" → 삭제
- 출처: 2026-07-07 ("괄호 설명… 어필력을 떨어뜨리는 표현")

### S-03 · 문장 · MUST · active
정량 성과는 "이전값 → 이후값" 전후 쌍으로 쓰고, 단축률(%)은 괄호 보조
표기로만 붙인다. 퍼센트 단독 표기 금지.
- 예: "빌드 90분 → 15분(약 83%)"
- 출처: 전 초안 공통 표기

### S-04 · 문장 · MUST · active
실행·성과 bullet은 명사형으로 종결하고(…구조화 / …자동화 / …단축 /
…확보), 문제·요약 등 산문 단락만 서술형 종결어미를 쓴다.
- 출처: 전 초안의 실행·성과 bullet 공통 (예외 없음)

### S-05 · 문장 · PREFER · active
한국어 문장 안에서 기술·항목을 나열할 때는 쉼표 대신 가운뎃점(·)을 쓴다.
- 예: "React·Vue·TypeScript", "Web·Admin·App"
- 출처: 전 초안 공통 표기

### S-06 · 문장 · PREFER · active
타깃 JD의 요구 키워드는 해당 실행·성과 항목 끝에 괄호 태그로 명시해 대응
관계를 드러낸다.
- 예: "…단계적 전환 (레거시 점진 전환)", "…도입 (AI 기능 실서비스 도입)"
- 출처: CJ ENM·두산·NHN 3개 타깃 문서 반복

## 내용 (C)

### C-01 · 내용 · NEVER · active
"팀 공동", "일부 기여" 같은 기여 축소 한정어를 노출 문구에 쓰지 않는다.
사실 관계는 experience-bank에만 유지하고 면접에서 정직하게 답변한다.
기여 경계는 프로젝트 헤더의 "[주요 업무]" 행(F-01)에서 사실대로 밝히고,
F-01 헤더가 없는 문서에서는 검증된 담당 범위를 주변 문장에 사실대로
드러내거나 해당 주장을 뺀다 — no-fabrication은 이 규칙보다 상위다.
- 출처: 2026-07-07~08 ("'팀 공동'은 빼줘" + target-companies.md에
  "되돌림 금지"로 기록됨)

### C-02 · 내용 · NEVER · active
블로그 링크(dahun429.tistory.com)는 지원 문서 본문·메타데이터 어디에도
넣지 않는다. 링크는 GitHub만.
- 출처: 2026-06-29, 2026-07-08 반복 지시

### C-03 · 내용 · MUST · active
강조 대상 구절은 타깃 직무의 요건·주요업무와 매칭되는 곳에만 선정하고,
타깃이 바뀌면 강조 지점을 다시 잡는다. 강조의 렌더링(볼드 등)은 매체가
지원할 때만 적용하며 `DESIGN.md`를 따른다 — 플레인 텍스트 폼에는 마크업을
넣지 않는다.
- 출처: 2026-06-27~29 반복 지시

**강조 배분 시스템 (2026-07-27 신설 — 인사·기술·헤드헌터 3자 자문 반영)**

강조는 예산이 정해진 희소 자원이다. 한 페이지에 4~6개가 임계점이며 8개를
넘으면 장식으로, 10개를 넘으면 기본 서식으로 읽혀 강조 기능을 잃는다.

**가중치** — 무엇이 볼드를 받는가

| 등급 | 대상 |
| --- | --- |
| W1a | 전후비교 수치 (`2.5초 → 1초`) — 맥락 지식 없이 읽히는 유일한 유형 |
| W1b | 금액·비즈니스 결과 |
| W1c | 기준선 없는 규모 (`3,493명`) — 예산 부족 시 먼저 자름 |
| W2 | 판단 기준 구절 — "무엇을 어떤 기준으로 결정했나" |
| W3b | 구현 특정성 토큰 (`getItemLayout`·`DTO 투영`·`4유형 오류 분류`) |
| W3a | 일반 스택 토큰 (`React`·`TypeScript`) — **금지**, 전 지원자 공통이라 정보량 0 |
| W4 | 구조 라벨 — 볼드 미사용, 라벨 티어(700)로 |
| W5 | 소유권·범위 (`리드`·`단독`·`총괄`) — 실행 섹션에서 예외적으로 살릴 후보 |
| W0 | **기준·대상 없이 홀로 선 동작어**, LOC — **금지** |

W0는 토큰 금지가 아니라 절(節) 기준이다. `설계`(단독)는 금지, `점진 전환
구조를 직접 설계`(대상 포함)는 허용, `변경·장애 빈도를 기준으로 전환 순서
결정`(기준 포함)은 최우선이다. 토큰 단위로 금지하면 볼드 후보가 명사(수치)
만 남아 "숫자만 강조" 편향이 생긴다.

**계층별 예산과 1순위** — 가중치는 전역 상수가 아니라 계층별 함수다.
계층마다 주 독자가 다르기 때문이다.

| 계층 | 주 독자 | 1순위 | 예산 |
| --- | --- | --- | --- |
| 요약 | 전원 | — | 0 |
| 핵심 성과 근거 줄 | 인사·헤드헌터 | W1a → W1b → W1c | 항목당 1 (총 4~5) |
| 경력 | 인사·헤드헌터 | 규모·전환 토큰·차별 문구 | 4 |
| 경력기술서 **실행** | 기술 | **W2 판단 기준** | 2~3 |
| 경력기술서 **성과** | 인사·헤드헌터 | W1a·메커니즘 동반 수치 | 2~4 |
| 기술 표 | — | — | 0 (열 구조가 이미 스캔 경로) |

**⚠ 2026-07-27 후반 소유자 지시로 아래 "계층별 예산"과 "배분 제약"의 절제
조항이 폐기됐다.** 새 기준은 **"볼드만 따라 읽으면 그 자체로 요약본이
되는가"**이며, 각 강조는 키워드가 아니라 **주어+결과가 담긴 절**이어야 한다.
페이지당 개수 상한 없음(실제 출고본은 경력기술서 페이지당 13~21개).

살아남은 조항은 셋뿐이다 — **라벨 티어(700 + body 색조) 유지**(원래의
"안 읽힌다"를 고친 실제 수정이므로 절대 800으로 올리지 않는다), **줄 첫머리
강조 금지**, **볼드 제거 테스트**. 아래 가중치 표는 *무엇을 고를지*의
우선순위로는 여전히 유효하다.

폐기된 조항도 근거를 남겨 둔다 — 3자 자문(인사·기술·헤드헌터)에서 나온
판단이므로, 되살릴지는 소유자가 결정한다. **증빙 필터도 함께 해제됐다**:
`needs_scope` 지표(`매출 1.0억` 등)가 현재 출고본에서 강조를 받고 있으므로,
헤드헌터가 경고한 "볼드는 면접관에게 여기 질문하라는 표지판" 리스크는
그대로 남아 있다.

**배분 제약 (폐기 — 이력 보존용)** — 개수 상한만으로는 균등 분포로 수렴하고,
균등 볼드는 무볼드와 같다.

- **불릿당 최대 1개**, 한 프로젝트에서 **볼드 없는 불릿 비율 50% 이상**
- **인접 금지** — 같은 줄 2개, 연속 불릿 볼드 금지
- **짝짓기** — 수치 단독 볼드 금지. 결과 명사구와 수치를 한 단위로 굵게 한다.
  `2주 납품`만 굵으면 스캔에 "무엇이 2주 걸렸는지"가 남지 않는다
- **증빙 필터** — `metric-registry.md`가 `confirmed`인 지표만 볼드 가능.
  `source_stated`는 스코프가 **같은 줄에** 있을 때만, `needs_scope`·미등재는
  **볼드 금지**. 문면 유지는 소유자 결정을 존중하되 강조만 제외한다 —
  볼드는 면접관에게 "여기 질문하세요"라는 표지판이다
- **반복 볼드 금지** — 같은 사실이 인접 계층(경력 ↔ 경력기술서)에 반복되면
  한쪽만 굵게 한다. 1페이지 ↔ 경력기술서는 독자 도달 시점이 달라 예외
- **조건부** — 조직 규모 수치는 같은 줄에 소유권 동사가 있을 때만 굵게 한다.

### F-08 · 구조 · MUST · active
요약·경력 등 **전면 섹션**은 지표 나열이 아니라 **정체성 → 강점 → 궤적**이

나열 대신 규모·사업 결과 중심의 큰 덩어리로 서술하고, 세부 수치는
경력기술서(아카이브 계층)가 전담한다 — 전면에는 시그니처 지표 한두 개만
남겨 중복 나열하지 않는다.

**계층별 임무 분담 (2026-07-27 흡수)**: 같은 사실을 두 계층에서 반복하지
않는다. 요약·핵심 성과·경력·경력기술서·기술은 각각 다른 임무를 맡는다 —
요약은 "누구인가"(정체성·궤적·기술 범위), 핵심 성과는 "자랑"(칩 + 근거

계층의 임무인지 정하고 나머지에서 뺀다. **의도된 중복은 문서에 예외로
