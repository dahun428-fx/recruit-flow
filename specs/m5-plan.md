## 0. 왜 M5인가 — 현 상태와 마찰

M1~M4는 구현·리뷰 머지 완료다. 2026-08-16 라이브 실행(빗썸페이 Frontend
JD)으로 엔진·에이전트·SSE·게이트 루프가 **실동작**함도 확인했다. 그러나
그 실행에서 "구현됨"과 "실제로 쓰기 좋음" 사이의 간극이 드러났다:

1. **JD 교체가 수동이다.** 새 JD로 돌리려면 문서 등록 + JD 입력 노드
   documentId 재배선을 손으로 해야 했다(이번엔 DB 스크립트로 처리). JD별
   맞춤이 이 도구의 핵심 반복 루프인데 그 루프가 가장 뻑뻑하다.
2. **결과를 이해하려면 DB를 열어야 한다.** 게이트 실패 사유·점수(5→12)·
   블로커는 채팅 카드에 일부만 있고, 회차 비교나 "무엇을 고쳐야 통과하나"는
   UI에 없다.
3. **증거베이스가 테스트 픽스처에 물려 있다.** 증거 입력 노드가
   `test-evidence.md`(그나마 cp949 깨짐)를 가리켰고, 실 증거베이스
   (experience-bank/profile 등)와 연결돼 있지 않았다.
4. **산출물이 축적되지 않는다.** JD별 결과물 보관·비교·이력이 없다.

**M5 목표**: 본인 이력서를 JD마다 맞춤 생성하는 반복 루프를 실사용 가능한
수준으로 끌어올린다. 사용 모델은 **본인=지원자, 증거베이스 고정, JD만
교체**(blueprint 결정 1, my-recruit 하네스의 UI화)로 확정한다.

## M5-0. 선결 정리 (실 DB — **사용자 승인 필수**)

이후 모든 워크스트림의 전제. 실 DB를 건드리므로 별도 승인 후 실행하고,
검증은 격리 DB에서 한다(CLAUDE.md).

- **깨진 문서 복구/정리**: `test-jd.md`·`test-evidence.md` 등 cp949/U+FFFD
  오염 문서를 UTF-8로 복구하거나 폐기. 방지 규칙은 이미 CLAUDE.md·
  [[recruit-flow-windows-cli-korean-trap]]에 있음.
- **canonical 파이프라인 실데이터 연결**: 증거 입력·에이전트 mount가 테스트
  픽스처가 아니라 실 증거베이스를 참조하도록 재배선.
- **고아 tool 노드 이관**(M4 잔여): "문서 검색 도구" tool 노드가 현재
  writer에만 mount돼 있고 채점 노드엔 없다. M4 결정 3(장착=Agent
  config.mounts 칩)에 맞춰 데이터 이관 스크립트로 옮기고, 채점 노드에도
  증거 접근이 필요한지 판정.

산출: 실 DB에서 빗썸페이 JD가 아닌 **본인 직군 JD**로 한 번 더 라이브 실행해
기준선 확보.

## 워크스트림 A — JD 교체 → 즉시 실행 (입력 루프) 【최우선】

가장 자주 반복하는 동작. 핵심 제약: **챗봇은 결정 5(add만)로 그래프를
재배선할 수 없다** — JD 입력 노드의 documentId를 챗봇이 바꿀 방법이 없다.
따라서 설계 포크가 생긴다.

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. "현재 JD" 고정 문서 규약** (추천) | JD 입력 노드는 stable 문서(예: "현재 JD")를 참조. 새 JD는 같은 이름으로 upsert(`register_document`/`edit_document`) → 노드가 자동으로 최신 사용 | 챗봇 사령탑(결정 9b)과 정합, 신규 표면 최소, 결정 5 무위반, 이력은 `document_versions`에 남음 | "현재 JD"라는 규약을 사용자가 알아야 함 |
| B. Input 노드 인라인 JD UX | 정의 탭/노드 카드에 "JD 붙여넣기" 필드 → 참조 문서 생성·갱신. 사람이 캔버스에서 | 노드가 JD를 소유, 재배선 불필요, 직관적 | 챗봇 루프 아님(수동) |
| C. "새 지원" 플로우 | JD 붙여넣기 → 입력 자동 세팅 + 실행을 한 번에 | 가장 매끄러움 | 신규 스펙 표면 큼 → **v2** |

**추천**: A안(챗봇 "작성해줘" 루프)을 1차, B안(정의 탭 JD 교체)을 보강으로
병행. C안은 v2. → 사용자 확인 필요.

- 스펙 델타: `engine.md`(챗봇 "현재 JD 갱신→실행" 규약), `ui.md`(입력 노드
  JD 교체 UX), `nodes.md`(input 노드 규약 명문화).
- 완료 기준: 채팅에 JD 붙여넣고 "작성해줘"만으로 맞춤 이력서 run이 시작된다.

## 워크스트림 B — 결과 이해·수렴

- **채점 결과 UI 렌더**: 채점 아티팩트 JSON(total/verdict/passBar/blockers)을
  노드 아티팩트 탭·게이트 카드에 구조화 표시(현재는 DB 조회 필요).
- **회차 비교**: run 내 iteration별(writer #1 vs #2, 점수 5→12) 추이·diff 뷰.
- **수렴 가이드**: 에이전트가 이미 반환하는 `blockers`를 "통과하려면 무엇을
  고쳐야 하나" 실행가능 목록으로 표면화. gate_failed가 막다른 길이 아니라
  다음 행동으로 이어지게.
- 스펙 델타: `ui.md`(아티팩트 탭 JSON 렌더·게이트 카드·회차 비교),
  `engine.md`(회차 데이터 노출).
- 완료 기준: DB를 안 열고도 실패 사유·점수 추이·다음 액션을 UI에서 안다.

---

## 워크스트림 C — 증거베이스 관리

- **실데이터 연결**(M5-0 연동): 증거 입력·mount가 실 experience-bank/
  profile 참조.
- **증거 편집·버전**: `edit_document`(M4 존재)를 문서 탭 UI로 노출, 사람 편집
  경로 확보.
- **인코딩 복구 도구**: cp949→UTF-8 문서 복구 유틸(일회성 + 임포트 시 검출).
- **JD-증거 매칭 사전점검**: 실행 전 JD 필수요건 vs 증거 커버리지를 미리
  보여줘 **직군 불일치를 2분 낭비 전에** 잡는다(이번 라이브 실행의 마찰
  직결). 경량 에이전트 또는 룰로.
- 스펙 델타: `ui.md`(증거 편집), `nodes.md`(사전점검 위치 — 신규 판정 필요).
- 완료 기준: 실 증거로 실행되고, 명백한 직군 불일치는 실행 전에 경고된다.

## 워크스트림 D — 산출물·이력관리

- **JD별 결과물 보관·비교**: run 히스토리를 JD 기준으로 조회·비교(blueprint
  v2 "run 히스토리 전체 탐색" **승격** — 승인 필요).
- **이력서 템플릿 품질/다양화**: v2 "출력 템플릿 3종+" 일부 **승격**(승인
  필요). 현재 default 1종.
- 스펙 델타: `schema.md`(run↔JD 연결 필요 시), `ui.md`(히스토리·템플릿 선택),
  `engine.md`.
- 완료 기준: 지원별 산출물이 남고, 과거 결과와 비교할 수 있다.

## 실행 순서

```
M5-0 선결 정리(실 DB, 승인 후)
  → A 입력 루프  → B 결과 이해   ← 핵심 반복 루프, 우선
  → C 증거 관리(매칭 사전점검은 B와 함께 가치)
  → D 산출물·이력
각 워크스트림: architect(분해) → 빌더 → code-reviewer → qa-verifier,
완료 시 npm run e2e 회귀 게이트(specs/e2e.md).
```
